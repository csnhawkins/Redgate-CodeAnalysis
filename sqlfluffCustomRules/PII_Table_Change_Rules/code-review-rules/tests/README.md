# Running the proof pair

Every rule domain in this package ships a "proof pair" — one migration where every statement should
violate, one where nothing should. You don't need a separate scratch Flyway project or a real
migrations folder to run them: point `check -code` at one script file directly with
`-check.scope="script"` and `-check.scriptFilename`.

```bash
# Every statement in this file should be reported. Check the count against the table below.
flyway check -code -check.scope="script" -check.scriptFilename="code-review-rules/tests/pii/V001__pii_violations.sql"

# Nothing in this file should be reported.
flyway check -code -check.scope="script" -check.scriptFilename="code-review-rules/tests/pii/V002__clean.sql"
```

`-check.scope="script"` reviews exactly the one file named by `-check.scriptFilename`, rather than
Flyway's configured `flyway.locations` — so this doesn't touch your project's real `flyway.toml`, and
there's no risk of the test migrations being picked up as real ones to deploy. `check -code` is static
analysis of the SQL text; as long as the dialect is set explicitly in `sqlfluff.cfg` (it is —
`dialect = tsql`), no database connection is required to run it.

Verified output on `V001__pii_violations.sql` (Flyway Enterprise 13.8.0-rc2848, SQLFluff 4.3.0 bundled):

```text

Total analysis: 1 SQL file(s) scanned with 43 Rule(s) and dialect TSQL applied
Files with violations: 1     Warning Violations: 0     Error Violations: 24

+------------------------+------------+------------------+----------+
| Engine                 | Rule Code  | Violations Count | Severity |
+------------------------+------------+------------------+----------+
| SQLFluff (Custom)      | PI01       | 13               | Error    |
| SQLFluff (Custom)      | PI02       | 7                | Error    |
| SQLFluff (Redgate)     | RG01       | 1                | Error    |
| SQLFluff (Redgate)     | RG09       | 2                | Error    |
```

`PI01` + `PI02` account for 20 of the violations above — the rest come from other active rules
(`RG01`, `RG09`, and Flyway's own regex-based checks) also matching statements in the same file, which
is expected since `V001__pii_violations.sql` isn't scoped to *only* trip the PII rules. When counting
programmatically (see below), filter to `PI01`/`PI02` specifically rather than the total violation count.

## Expected counts

Run each domain's script on its own — mixing two domains' test files into one report makes the total
meaningless, since you can no longer tell which domain's rule produced which count.

| Concern | Test file | Expected violations (that rule's codes only) |

| PII (`PI01`/`PI02`) | `tests/pii/V001__pii_violations.sql` | **20** (`PI01`: 13, `PI02`: 7) |
| PII (`PI01`/`PI02`) | `tests/pii/V002__clean.sql` | **0** |

the checklist for adding one.

## Reading the output

This is standalone `flyway check -code` output, reporting through its own summary table plus whatever
report formats you've configured (HTML, JSON, SARIF — all three are generated by default). To pull an
exact count for one rule programmatically — the form the CI assertion in the root `README.md`
(section 6) is based on — request a JSON report and filter by rule code rather than counting every
violation in the file:

```bash
flyway check -code -check.scope="script" -check.scriptFilename="code-review-rules/tests/pii/V001__pii_violations.sql" -reportFilename=pii-test-report.json

jq '[.individualResults[].results[].violations[] | select(.rule.code == "PI01" or .rule.code == "PI02")] | length' pii-test-report.json
```

> Not from Redgate docs — the flags and JSON shape above match a real verified run; re-check the exact
> JSON path if you're on a different engine version, since the report schema has changed across
> releases (see the root `README.md` section 5).

If the count comes back lower than the table above, don't assume the rule is broken until you've ruled
out the two silent-failure modes that produce a low-but-not-zero or zero count with exit code 0 anyway:
the file-size skip limit, and a rule that's stopped loading or been dropped from `sqlfluff.cfg`'s
`rules =` line. Root `README.md` sections 5 and 6 cover both.
